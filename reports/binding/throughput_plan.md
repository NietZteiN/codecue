# Throughput optimization plan

The user requested maximum practical GPU throughput. This is performance engineering on the existing checkpoint and public prompts; the completed scientific runs and their source snapshots stay unchanged. No new checkpoint, dependency installation, training, or generated final-test evaluation is required.

Use the first 256 release-order CRUXEval questions in each of the direct and CoT completion protocols (512 requests per timed candidate). Preserve exact reference prompt-token IDs, BF16, greedy decoding and the 512/1,024 new-token ceilings. Compare the original eager batch-eight CPU-decoding stop loop against GPU-side StopStringCriteria, built-in SDPA attention with batches 8/16/32/64/96 and input-length bucketing, and the installed vLLM continuous-batching engine with request chunks 64/128/256. vLLM uses at most 256 active sequences, a 16,384-token scheduling budget, chunked prefill and a 90% GPU-memory target. Clear its prefix cache between timed trials so repeated full-prompt cache hits do not favor later candidates; common-prefix reuse within a real trial remains enabled.

Time synchronized generation including decode/stopping and output extraction. Report model loading, warmup/compilation and whole-worker time separately. Count useful output tokens rather than EOS-valued padding. Sample utilization, memory and power from the allocated device. Record OOM/failure/timeout candidates, clean up only the profiler's own worker process group, and retain successful earlier trials. Independent worker processes isolate backend initialization and CUDA memory. All workers must hold the parent stage's active shared GPU-budget lease.

Select the highest requests/second among completed candidates that preserve prompt IDs, one completion per request and generation ceilings. Do not choose by answer accuracy. Retain raw responses and exact/value/validity/correctness agreement with the completed reference, because batching and numerical kernels can change outputs. The fastest performance configuration is a separately recorded execution profile; it does not replace or retroactively alter old scientific scores.

Validate the selected configuration on all 1,600 released direct/CoT requests. For vLLM, queue the full backlog while retaining the profiled effective concurrency, so slots can immediately accept new requests as old ones finish. Save the selected worker specification and full validation metadata for subsequent runs. Keep an eager replay mode available for strict historical comparisons.

Use one allocated H100/H200 at a time and charge the entire profiling/validation stage to the existing four-GPU-hour single-checkpoint ledger. The stage ceiling is 3,600 seconds, including backend startups and failed attempts, with 600 seconds initially reserved for final validation. Exclude the known MIG node. H200 eligibility follows the inherited documented fallback if H100 is occupied; record the reason in submission metadata and the actual GPU in results. Shared normal/H200 requests remain inside their four-job limit. This prioritizes useful throughput within the existing resource cap.

Implementation uses the installed package APIs and primary documentation: [vLLM optimization](https://docs.vllm.ai/en/stable/configuration/optimization/) and [Transformers attention backends](https://huggingface.co/docs/transformers/attention_interface). The actual installed versions, worker logs, configurations and frozen source are retained under `artifacts/binding/throughput/`.

The original 128-per-protocol profile request was cancelled while pending, before any GPU experiment. The enlarged 256-per-protocol cohort tests a full 256-request batch of each protocol rather than relying on a mixed-protocol batch. It uses the same tested source code with a new configuration/preflight identity.

## Runtime repairs and revised validation

The installed vLLM wheel targeted CUDA 13 while the working PyTorch environment targets CUDA 12.9. A verified official vLLM 0.26.0 CUDA 12.9 wheel is extracted under the project's throughput runtime directory; the shared environment is unchanged. Its download URL, SHA-256 and upstream release digest are recorded in `artifacts/binding/throughput/runtime/vllm_cu129_manifest.json`. The entrypoint sets `CUDA_HOME=/usr/local/cuda-12.9` and disables the unused FlashInfer stochastic sampler for this greedy workload. The repaired binary must pass a CPU import/ABI check before GPU execution. The worker script has a Python spawn guard so engine subprocesses cannot recursively invoke the profiler.

The initial static-batch sweep retained successful trials but exceeded its worker timeout. The controller now preserves those completed trial artifacts on timeout, and requires a complete full-workload validation before calling the stage successful. Its cancelled reservation was reconciled against terminal SLURM accounting. Failed startup time remains charged to the shared GPU ledger.

The v4 sweep uses one engine for all three 512-request profiling candidates and subsequent 1,600-request validation candidates at request chunks 128, 256 and 1,600. The final chunk is the full backlog, allowing continuous admission without intermediate call barriers. Prefix caches are cleared before each candidate. Select the fastest complete full-workload candidate by requests/second and retain all candidate outputs and quality differences. Reusing the loaded engine avoids paying for a second model load, compilation and graph capture. Whole-worker timing includes both profiling and validation and is labeled accordingly; generation timing is reported separately for every candidate.

The v4 stage reserves at most 1,800 seconds from the existing ledger, with a 1,680-second worker timeout. It uses UUID-verified allocated-device telemetry, avoiding ambiguity from SLURM's local CUDA index remapping. Submitted job IDs and immutable source are in `jobs_v4.json` and `source_v4.json` under `artifacts/binding/throughput/`. An after-success CPU audit rechecks every saved candidate's exact prompt tokens, coverage, scores and timing calculations before exporting a reusable execution preset.
